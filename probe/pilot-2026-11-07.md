# Pilot run, 2026-11-07

Four clients from the structured-content research pins, plus the fx JavaScript adapter and the TypeScript SDK's own client, run against the tool result fixtures. Each client's records are in `runs/<client>@<version>/` and collected in `../data/verified/<client>.json`. The verdicts below use the clients page glyphs: `[…]` content, `{…}` structuredContent, `⟨…⟩` the whole envelope, `"…"` a placeholder.

## Observed against read

Every default-config observation agrees with the client's research note on the three results the clients page tabulates, and on the variants the notes cover. The list below is every point where the probe adds to or differs from the note or the page.

**codex** (`at: 2025-06-18`, Responses API)

- Agrees: `{…}` only for summary-and-data and structured-only; mirror once; the `audience: ["user"]` block is dropped with the rest of `content` because `structuredContent` wins (the note's "annotations are not read on the model path" is not separable from that in this fixture set); `isError` text comes from `structuredContent`; no outputSchema validation (`schema_mismatch` reaches the model as `{…}`); app-only tool hidden; `{}` replaces content (model sees `Wall time: … Output:\n{}`); `sc_string` reaches the model as a quoted JSON string; `sc_null` falls back to `content`.
- Adds: every payload is prefixed with `Wall time: <n> seconds\nOutput:` as the note says; the probe records the exact text. A result with no `content` key, sent over the raw path, reaches the model as `{…}` (rmcp defaults the missing array). An empty `{}` result reaches the model as two text items, the `Wall time` header and `tool call error: tool call failed for \`probe/probe_empty_object\` … Unexpected response type`, rmcp's deserialization failure in codex's wording.
- Page cell "Content empty: `{…}`" confirmed. Page cell "Summary + data: `{…}`" confirmed.
- Not in the note: the model sees MCP tools inside a `namespace` tool named `mcp__<server>`; the function keeps its bare name. The note describes the `mcp__server__tool` qualification only on the client side.

**goose** (`at: 2026-07-28`, both the OpenAI and the Anthropic formatter)

- Agrees on every fixture: `[…]` only; `(empty result)` when `content` is empty or missing; the `audience: ["user"]` block is dropped and the plain block arrives; `isError` text from `content`; no validation; app-only tool hidden; `{}` and `null` and a string `structuredContent` all ignored. The image arrives as a native `image` block inside `tool_result` on the Anthropic formatter; on the OpenAI formatter, where goose does not know the mock model supports vision, it is replaced by the sentence `This tool result included an image that was omitted as the model does not support vision.`
- Adds: an empty `{}` result over the raw path reaches the model as `The tool call returned the following error: -32603: -32603: Unexpected response type` (OpenAI) and `Error: -32603: -32603: Unexpected response type` (Anthropic), so the rmcp deserialization failure is surfaced to the model with the SDK's wording.
- Page cells confirmed: `[…]` audience-filtered, `"…"` for content empty.

**mastra** (`at: 2026-07-28` by default, `2025-11-25` with `protocolVersion: legacy`)

- Agrees: without an `outputSchema`, `{…}` replaces `content` (summary-and-data, structured-only, with-image, audience-user, large); with a matching `outputSchema`, `[…]` text (schema-match); `isError` under the default `onToolError: 'throw'` gives the model the content text; `onToolError: 'return'` gives it the envelope; app-only tool not offered; `{}` takes the structured path, so the model sees `{}` and nothing from `content`; `sc_null` gives `null`; a string `structuredContent` reaches the model as the string.
- Adds: on a schema mismatch the SDK's own error text reaches the model verbatim (`Structured content does not match the tool's output schema: data must have required property 'issues'`), and so does the SDK's parse error for a content-less or empty result (`Invalid result for tools/call: … expected array`). The note has the first; the second is new.
- Page cells confirmed, including the "it depends on outputSchema" row.

**fx native** (`at: 2026-07-28`)

- Agrees: `⟨…⟩` with `{"server","tool","result":{content, structuredContent, isError}}` on every well-formed fixture; mirror arrives twice; content-less and `{}` results end the call with `MCP server 'probe' ended the call: the server's answer was malformed …`; `sc_null` arrives as content only (null dropped); the image block arrives as `{"type":"image","mimeType":"image/png","delivery":"image content"}` with a notice line prepended.
- Adds, and differs from the page's single `⟨…⟩` cell: for the 64 KiB result the model got the whole 41 KB text block and no `structuredContent` at all. That is the note's "without a store … `collect_result_text` follows only `text`, `data`, `blob` and `content`" branch, reached here because `fx ask --no-save` has no session store. The page cell for fx should carry a size caveat.
- `app_only`: fx offers the app-only tool to the model and the model calls it. The note says `_meta.ui.visibility` has no effect; confirmed.

**libfx** (`at: 2025-11-25`, the TypeScript client's default negotiation)

- Agrees: text, newline, compact JSON when both fields are present; mirror once (byte-identical text dropped); `{…}` when `content` is empty; `sc_empty` gives `text\n{}`; the SDK client rejects `sc_string` and `sc_null` on the 2025 era and the model sees its error text; schema mismatch gives the SDK's validation text.
- Adds: the 64 KiB result is replaced by `Host tool result exceeded the configured limit`, a libfx cap the note does not mention. An empty `{}` result reaches the model as an empty string.
- Not a disagreement, a precondition: the SDK client's default negotiation lands on 2025-11-25 here, so the libfx row is an initialize-era row. `ts-sdk-client` with the `auto` config shows the same; the SDK 2.4.0 client does not lead with `server/discover` unless asked.

**TypeScript SDK client** (no model)

- `callTool` returns the whole envelope. On 2025-11-25 it defaults a missing `content` to `[]` and rejects a non-object `structuredContent`; it throws on an outputSchema mismatch (`Structured content does not match …`). `registry/sdk-compat.json` holds the server-side half of the same matrix.

## Coverage

Cheap to probe, no person needed: anything with a non-interactive command or a library entry point and a configurable model endpoint. Of the clients list that is codex, goose, mastra, fx, libfx, opencode, cline's CLI, fast-agent, hermes-agent, openclaw, pi, and the Python frameworks (strands, crewAI, deepagents, adk-python, agent-framework). Every spec feature visible on the wire is in reach for them with the existing capture: initialize capabilities, `server/discover`, roots, list-changed handling, elicitation and sampling replies need scenario handlers on the fixture server and classifiers, not new capture points.

Needs a person or a browser: Zed, VS Code, Kilo Code's extension, LibreChat's UI, and the closed hosts (Claude Desktop, Cursor, ChatGPT). For those the fixture server still works as the instrumented endpoint, and the wire half of the record (what the client declared, what it called, what came back) is captured without a model mock; the model half needs the host's own provider setting pointed at the mock, which GUI hosts do not all allow.

Not yet run here: code mode and script routes (goose `code_execution`, mastra code mode, codex code mode), which the adapters leave as named configs to fill in; Gemini-API shapes for adk-python; the `legacy`-only and `modern`-only era policies against clients other than mastra and the SDK client.

## Schema and vocabulary changes

- `Evidence` gained `clientVersion`, `config`, `artifact`, `observation` and `run`. The reason for `observation` over a sidecar file: the record stays one object a card or a page can render, while the detail is typed per scenario family under `ProbeObservation` (a `oneOf`), so a new family adds a member without touching `Evidence`. `clientVersion` is on the evidence row because a verified record is about one build and the registry entry is about the client.
- New `schema/verified-evidence.schema.json` for the generated `data/verified/<client>.json` overlays, validated by `scripts/validate.js`, which also checks every capability id in them against `spec-versions.json`.
- `spec-versions.json` gained `tools.result.content`, `tools.result.structuredContent`, `tools.result.outputSchema`, `tools.result.audience`, `tools.result.isError` and `tools.result.media`, and the ui extension gained `alias: apps` with `apps.visibility` and `apps.resourceUri`. The naming rule is recorded in the file's `capabilityIdScheme`: dotted paths following the wire field names, rooted at a core primitive, or at an extension's alias since reverse-DNS names do not nest in a dotted id.
